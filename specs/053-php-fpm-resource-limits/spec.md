# PHP-FPM resource limits (cgroups)

Contain each hosting account's PHP-FPM websites with cgroup v2 limits so one
account cannot exhaust CPU, memory or processes on a shared webserver. An account
(ISPConfig client) is a systemd slice; each of its PHP-FPM pools runs in its own
service inside that slice. Limits are set by administrator keys on the client, as
the product PHP policy is, and applied by a root worker on each webserver.
Research and spike results: [research.md](research.md).

## Scope

- Administrator-only `web_resource_limits` on `POST/PUT /clients` and in client
  detail. Omission preserves; `null` removes. Client and reseller keys cannot
  set it and never see other accounts' limits.
- Account limits (slice): CPU as percent of one CPU, memory in MiB, tasks
  (processes + threads). Optional per-website limits (pool service) with the same
  three fields. Every limit is nullable (= unlimited at that level). An object
  with all limits null still isolates pools, for accounting and usage display.
- Scoped keys read their own account's limits, the webserver capability and the
  measured usage (account and per website) with freshness metadata.
- New server-tools component `php-limits` (web role) installs the worker, the
  systemd drop-ins and the SQL grants.

Out of scope for this spec: cron jobs, SSH/SFTP sessions and WordPress Tools
commands (they run outside PHP-FPM; follow-up can place them in the account slice),
block-I/O limits (device-specific; `io.max` needs major:minor per backing device and
`IOWeight` depends on the I/O scheduler), memory throttling (`MemoryHigh`, see
research), cgroup v1 hosts, non-systemd hosts, and PHP modes other than PHP-FPM
(fast-cgi/mod_php run under the webserver and are reported as not contained).

## Server design

Units and naming (all generated by the worker, marked as managed):

- `ispconfig.slice` — parent, no limits of its own (administrators may add a
  drop-in to cap all hosting on the server).
- `ispconfig-client{ID}.slice` — account limits: `MemoryMax`, `MemorySwapMax=0`,
  `CPUQuota`, `TasksMax`, with CPU/memory/tasks accounting on.
- `ispconfig-php-web{DOMAIN_ID}.service` — one php-fpm master for exactly one
  pool, `Slice=ispconfig-client{ID}.slice`, `Type=notify`, `OOMPolicy=continue`,
  `Restart=on-failure`, the distribution unit's hardening, optional website limits.
  `PartOf=` and `WantedBy=` the version's distribution unit so ISPConfig's restart
  mode, stop and boot follow the shared service. Its master configuration copies the
  distribution `[global]` settings, logs to syslog and includes only
  `pool.d/web{DOMAIN_ID}.conf`, which ISPConfig keeps writing unchanged.

Shared master: a drop-in on each managed `phpX.Y-fpm.service` points `ExecStart` at a
generated copy of the distribution `php-fpm.conf`. Its pool `include=` glob is replaced
by one explicit `include=` per pool file that is **not** isolated (`www.conf`, the REST
pool, ordinary websites), using the real `pool.d` paths. php-fpm only warns when an
explicit include matches nothing, so a pool ISPConfig deletes before the hook runs
cannot break the shared master (a dangling symlink matched by a glob would).
Distribution files and ISPConfig templates are not edited, so package upgrades keep
working and ISPConfig regenerates pools as before. Only distribution units whose
`ExecStart` is exactly `/usr/sbin/php-fpmX.Y --nodaemonize --fpm-config
/etc/php/X.Y/fpm/php-fpm.conf` and whose configuration includes `pool.d/*.conf` are
managed; others are reported and left alone. A changed `ExecStart` takes effect on
the next start, so installation restarts each newly managed service once, and no pool
of a service is isolated while its running master still uses the distribution file
(checked on the master's command line).

The same drop-in runs `ispconfig-php-limits hook` before and after the shared master's
start and reload (`-` prefixed: a hook failure never blocks the distribution service):

1. before: read the local policy state; stop units whose pool file disappeared or whose
   account lost isolation and confirm their listener is gone; write the include list
   (every pool except isolated ones); regenerate unit files/slices when changed
   (`daemon-reload` only when a file changed);
2. the distribution `ExecReload` (`kill -USR2`) or start;
3. after: `--no-block` start newly isolated units (each unit's `ExecStartPre` waits
   until the shared master has released its socket), reload isolated units whose pool
   file changed.

Invariant: a pool is never included in the shared master while another master listens
on its socket, and never isolated while the shared master may still load it. Any pool
not positively confirmed as isolated stays in the shared master (fail-open for
availability); if planning fails, the hook falls back to "all pools except the ones
whose isolated unit is active". A pool whose own unit fails while its pool passes
`php-fpm -t` falls back to the shared master and is reported `fallback`; a pool whose
configuration is invalid stays isolated (it would break the shared master too).
Concurrency: the cron worker never holds the sync lock while it asks systemd to reload a
PHP service, because that reload runs the hook, which takes the lock.

Worker: root cron every minute (`ispconfig-php-limits run`), using the server's
existing ISPConfig master database credentials like the other workers. It reads
account limits, writes the local policy state atomically, runs the same sync for
every managed PHP service, then samples cgroupfs and writes heartbeat and usage.
Hooks only use the local state, so ISPConfig reloads never depend on the master
database being reachable. Changing limits rewrites slice/unit files and runs
`daemon-reload`, which applies new values to running cgroups without restarting
PHP (verified on isp-test).

Requirements, refused with a status message instead of partially installing:
cgroup v2 unified hierarchy with `cpu`, `memory` and `pids` controllers, systemd with
`OOMPolicy` (243+), Debian/Ubuntu php-fpm units, PHP CLI 8.3+ with pdo_mysql for the
worker (as for the other server tools).

Uninstall/disable: restore every isolated pool to the shared master, remove the
drop-ins and generated units, `daemon-reload`, restart nothing that is not managed.

## Usage and status

Per account slice and per isolated pool on each server: `memory.current`,
`memory.peak`, CPU percent over the last sample interval and last 24 h, throttled
time, `oom_kill` events (last 24 h and since the unit started), `pids.current`, and
the effective limits. Per website: `state` = `isolated`, `pending`, `fallback`,
`not_fpm` (with the PHP mode) or `failed`, and a short admin-safe reason. The worker
keeps a bounded local sample ring for the 24 h figures. Heartbeat expiry and
freshness follow the existing worker and usage patterns.
